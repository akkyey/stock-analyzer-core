## 1. 背景と課題

Google Colab 上での検証（初回構築および継続実行）において、以下の「表示と実態の乖離」および「ユーザーの違和感」が確認された。

1. **所要時間表示の乖離**:
   - 初回構築モードにおいて、ノートブック上で「所要時間は約 8〜10 分」と案内されていたが、実測は **約 20.0 分**（市場データ取得 12.2 分＋前処理・EDINET同期・DB構築等）であった。
   - 以前の並列ダウンロード（マルチスレッド）時代の古い固定文字列が残っており、Yahoo Finance 429 規制対策でシングルスレッド化した現状と合致していなかった。
2. **銘柄数推移の不透明さ（3920 → 3912 → 3890）**:
   - ログ上で理由の説明なく数字が遷移するため、データの欠落やバグと誤認されやすい。
     - `3,920`: JPX 公式リストからの銘柄マスタへの初期登録数
     - `3,912`: 同梱の財務シードの件数。**件数の差（8）は「新規上場の数」ではない**。シードには上場廃止済みの会社も含まれ、取得対象のうちシードに無い銘柄（シード作成後の新規上場）は別に数える（2026-10-03 の空の DB の実行では 43 社）
     - `3,890` 前後: **銘柄マスタの月次同期** (JPX の最新一覧との同期: 新規上場の追加・上場廃止の除外) の結果。2026-10-03 の空の DB の実行では、新規 43 / 上場廃止 71 で 3,892 になった。PRO Market 等の再取得停止は、3 回連続で取得できなかった銘柄を 30 日止める仕組みなので、**初回は 0 件**で、2 回目以降に効く
3. **前処理中の沈黙時間**:
   - `🚀 パイプライン実行を開始します...` から `📡 全 3890 銘柄の市場データ取得を開始します...` まで、EDINET API 通信やキャッシュ読み込み等の処理が裏で実行されているが、コンソール表示がないためフリーズしたような体感を与える。
4. **取得完了内訳の表現不足**:
   - 成功件数（3,846 件）と失敗件数（44 件）が別々に表示され、母数（3,890 件）との整合関係が直感的に分かりにくい。

### 2.3 追補 (2026-10-05 夜): Colab 1 回目の実測を受けた修正

Colab での 1 回目 (初回構築、`release/v1.3.0` の `52085d6`) の実測と画面を確認し、次の 3 点を直した。

| 画面の事象 | 実測・原因 | 対応 |
| :--- | :--- | :--- |
| 「約 18〜20 分」と案内したが、実測は **7.8 分** (株価取得 420 秒) | 10-02 の 20 分は、その日の通信の混み具合による。通信の回数は初回と 2 回目以降でほぼ同じ (約 195 バッチ) | 初回・2 回目以降とも「約 8〜10 分 (混雑時は 20 分程度まで)」。2 回目以降の「約 5〜8 分」は実測の裏付けが無く、設計 (§3.3 の通信回数) とも合わなかったため取り下げた |
| 初回でも「キャッシュ有効」と表示 | 初回は DB もキャッシュも無く、全書類をダウンロードしている | 取得済み (キャッシュ) の書類が 1 件以上ある場合だけ、「取得済みの N 件はキャッシュを利用」と出す |
| 株式分割の記録件数が画面に出ない (INFO ログのみ) | 今回の主な変更の動作が、画面から確認できなかった | 「株式分割: 新たに N 件を記録、株価を調整した銘柄 M 件」を 1 行出す (記録も調整も 0 件のときは出さない) |

- **2 回目 (差分) の実測と、表示の追加修正**: 2 回目は 438 秒 (7.3 分)。取得計画は 197 バッチ (1 年分 59 銘柄 = データなし 44 + 履歴が 20 行に満たない新規上場 15、差分 3,831 銘柄)、エラー 0。`stock_splits` は 263 件 (CLI の最終検証と同数)、`app_meta` の 4 キーが揃い、1 回目と 2 回目のレポート 2,090 行は全項目一致した。
  - EDINET の完了表示: 2 回目に「開示書類 269 件を反映 / 取得済みの 271 件はキャッシュを利用」と出たが、「反映」は保存済みの取得結果を毎回 DB に当て直した件数で、新規取得の数ではなく、紛らわしかった。「新たに取得 N 件 / 取得済み N 件はキャッシュを利用 / 反映した開示書類 N 件」に分けた (キャッシュ 0 件のときは、その項目を出さない)。
  - 診断サマリ: Drive が「未マウント」と出て、「Drive同期: 成功」と矛盾して見えた。Step 3 の完了時に同期を確定させてアンマウントするためで、「この時点ではマウントされていません (…同期の成否は「Drive同期」の行を参照)」に改めた。あわせて、データベース欄に `stock_splits` の件数、`edinet_documents` の状態別件数、`app_meta` の全キーを追加した (古い DB で、該当テーブルが無い場合は省く)。

- 1 回目の画面の数字は整合していた: 3,920 + 新規 55 − 上場廃止 85 = 3,890 (取得対象)。シードに無い 63 銘柄 = 新規上場 55 + 以前からシードに無い 8。データなし 44 件 (3,890 − 3,846) は、CLI の検証 (3,892 − 3,848) と同じ件数。
- 取得できなかった銘柄のバッチごとの警告 (`取得できなかった銘柄: N/20 件`) は、約 30 行並ぶ。レート制限による欠落も同じ警告で見えるため、今回は変更していない。

### 2.4 追補 (2026-10-06): 画面の文言と、案内の追加

| 変更 | 内容 | 理由 |
| :--- | :--- | :--- |
| 「シード」を、利用者に見える文言から外す | 画面: 「**同梱の財務データ**から N 銘柄を初期登録しました (…同梱データの作成後の新規上場等で未収録…)」「財務データを、**新しい版の同梱データ**で N 銘柄更新しました (決算期の新しい値は変更していません)」。ノートブック Step 0 の `refresh_fundamentals` の説明、利用ガイドも同様 | 「シード (種)」は開発側の用語で、利用者には何を指すか分かりにくい。**同梱**は、ツールのコード本体と一緒に配布していること (リポジトリの `src/resources/fundamentals_seed.parquet`)。INFO ログとコード内の名前は変えない |
| EDINET 完了表示で「反映 0 件」を出さない | 反映が 0 件のときは、「反映した開示書類 0 件」の項目を省く (「新たに取得 0 件 / 取得済み N 件はキャッシュを利用」は出す) | DB が最新で、当て直す結果が無いだけなのに、欠けたように見えるため |
| DuckDB の接続残りの案内 | 別のセルで DB を読み取り専用で開いたまま閉じていないときの `ConnectionException` に、「【DB の接続が、別のセルに残っています】… `with duckdb.connect(...) as con:` の形で必ず閉じるか、ランタイムを再起動してください (保存済みのデータは壊れていません)」を付ける | Colab の確認用のセルで実際に起きた (Step 3 が異常終了)。DuckDB のエラーだけでは、原因が分からない |
| 利用者への周知 | 利用ガイド (Step 3 の後) とノートブック Step 0 に、「v1.3.1 の最初の実行で、判定が約 16% の銘柄で変わる」旨と、更新を止める方法を追記 | 旧い決算期の値が、新しい決算期の値に更新されるため (§設計書 `data_validity_and_hybrid_fetch_architecture.md` 3.3) |
