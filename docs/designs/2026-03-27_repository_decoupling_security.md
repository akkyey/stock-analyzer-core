# 設計深化：Repository Decoupling & Security (v29.1)

## 1. 背景と課題

`stock-analyzer4` から `stock-analyzer-core` へのリブランディングに伴い、汎用エンジンと独自の投資戦略（Private な `stock-ops`）の物理的分離を断行した。シンボリックリンクの撤去とプラグインバリデーションの導入により基礎は固まったが、以下の運用上の課題が残っている。

### 課題A：開発効率と隔離のトレードオフ
シンボリックリンクがない環境下では、`stock-ops` 側の開発（新しい戦略の試作）を行う際に、`core` 側のバイナリをどのように参照・更新するのが最適か？

### 課題B：内部ドキュメントと ADR の分離
現在、意思決定記録（ADR）や設計書は `core/docs` に配置されている。これらには将来的に公開してはならない「秘伝のタレ」を含む可能性がある。

### 課題C：不慮の混入（Accidental Leak）
`.gitignore` の不備や Docker ビルド時の不用意な `COPY . .` により、Core リポジトリに Ops 側の秘密情報が紛れ込むリスク。

---

## 2. 提案と論点

### 2.1 ドキュメント階層の三層定義 (Proposed)

ドキュメントの性質により、配置場所を明確に分離する。

| 階層 | 配置リポジトリ | 内容例 | 公開可否 |
| :--- | :--- | :--- | :--- |
| **Layer 1: Engine Docs** | `stock-analyzer-core` | APIリファレンス、設計思想 (Public)、Pydantic 定義 | **YES** |
| **Layer 2: Decision Log** | `stock-analyzer-core` | アーキテクチャ決定（v29, v30等）、高速化手法 | **YES** (機密除く) |
| **Layer 3: Strategy Ops** | `stock-ops` | 具体的な戦略パラメータの意図、銘柄選定メモ、DB構造詳細 | **NO** |

**論点1**: `decision_log.md` から機密情報を抽出・分離するタイミングはいつか？（今すぐか、公開直前か）

### 2.2 開発環境の標準エージェント所作 (Standardization)

シンボリックリンクに頼らない環境開発。

- **案1: PYTHONPATH による解決**:
    - 環境変数 `PYTHONPATH` に `stock-analyzer-core` を指定した状態で `stock-ops` 側で作業する。
- **案2: 開発用 Docker Compose**:
    - `core` と `ops` を別のボリュームとしてマウントし、コンテナ内でのみ結合する。

**論点2**: 開発効率と「戻し忘れ」防止を両立するデファクトスタンダードはどちらか？

### 2.3 セキュリティ：プラグイン・インジェクションの深掘り

- **現状**: `yaml.safe_load` + `StrategyConfig` (Pydantic) により、型レベルの防御は完了。
- **追加対策案**:
    - **正規表現バリデーション**: `persona` や `default_style` に、コマンドを誘発するような特殊文字が含まれていないかのチェック。
    - **Resource Limit**: ロードできる YAML のサイズや個数に上限を設け、DoS 的な負荷を防止。

**論点3**: 分析エンジンの「外部性」をどこまで許容するか？（自作 Python スクリプトの注入を認めるか、YAML のみか）

### 2.4 コンテナ化テストへの移行と「隔離」の課題 (New)

コンテナ環境への全面移行にあたり、以下の技術的懸念がある。

- **ビルド時の秘密情報混入リスク**:
    - 現行の `Dockerfile` は `COPY . .` を採用している。Core リポジトリ内に一時的に置いた `stock-ops` 由来のファイルがレイヤーに焼き付くリスク。
    - **対策案**: 厳格な `.dockerignore` の適用、またはマルチステージビルドによる最小限の `src` コピー。
- **外部ボリューム依存の複雑化**:
    - `docker-compose.yml` で `./stock-ops/config:/app/config/external` のように外部ディレクトリをマウントする必要がある。
    - **懸念**: ホスト側のディレクトリ構造の差異により、CIや他開発者環境で「動かない」問題の発生。
- **データ不整合と競合**:
    - テスト実行時にマウントされた `data/stock_master.db` が本番用かテスト用か。
    - コンテナ並列実行時の SQLite ロック。

**論点4**: テスト用コンテナにおいて `stock-ops`（戦略定義）を「イメージに含める」べきか、常に「マウント」すべきか。
- **含める案**: 再現性は高い。しかし、Docker のレイヤー構造上、一度 `COPY` されたファイルはイメージから抽出可能であるため、Public な Docker Hub 等に Push する場合、**戦略情報も事実上の公開状態**となるリスクがある。
- **マウント案**: 公開用イメージとして清浄な状態を維持できる。ただし、ホスト環境のディレクトリ構造（Core と Ops の位置関係）に依存するため、ポータビリティが低下する。

**考察 (v29.1)**:
「見えるわけではない」という認識は、実行中のコンテナ内では正しいが、イメージ配布の観点では危険である。一度 `COPY` されたものは、例え後続のレイヤーで `rm` しても、レイヤー履歴を遡ることで物理的に復元可能である（`docker save` や `dive` 等のツール）。
したがって、**将来的に Public 公開を目指す `core` イメージには、build 時に `stock-ops` を COPY してはならない**。

**解決案**:
1. **開発・本体用**: `stock-ops` は一切含まず、空の `config/strategy` を持つ「純粋な Core イメージ」をビルドする。
2. **テスト・実行時**: `docker-compose` 等を用いて、ホスト上の `stock-ops` をボリュームとしてマウントし、実行時のみ結合する。
3. **CI用**: CI プロセス内で一時的にマウントまたは環境変数で戦略を注入し、イメージそのものを配布（Push）しない。

**追加の論点: Public レジストリの公開範囲 (v29.2)**:
「公開（Public）」とは、Docker Hub や GitHub Container Registry において、**全世界の誰もがそのイメージを `docker pull`（ダウンロード）可能である**ことを意味する。
- 誰でもダウンロードできるということは、前述の通り、イメージ内のレイヤーを解析して、含まれているファイルをすべて閲覧・抽出できるということである。
- たとえコード（`.py`）を秘匿しても、YAML などの設定ファイルがイメージに含まれていれば、それは事実上のオープンソース化と同義である。
- したがって、独自戦略（アルファ）を守るためには、**配布（Push）を前提とするイメージには物理的に情報を載せない**ことが、決定的な防衛ラインとなる。

### 2.5 ボリュームマウント方式の詳細と技術的懸念 (New)

ボリュームマウントを採用する場合、以下の実務的な「工夫」が必要となる。

- **UID/GID の不一致問題**:
    - **ホストOS側のユーザー**: あなたがマシンにログインしている時の ID（例: `irom` ユーザーは `1000` 番）。物理的なファイルはこの ID で管理されている。
    - **コンテナ内のユーザー**: `Dockerfile` で定義された `stockuser`。デフォルトでは別の ID に割り当てられることが多い。
    - **技術的補足**: Git 自体はファイルの UID/GID を保存しない。しかし、**ボリュームマウント（マウント）** は、ホスト上の「今そこにあるファイル」の ID をそのままコンテナに見せるため、この問題が発生する。
    - **結果**: コンテナが「ホストのファイルを読もう」とした時、ID が異なると「他人のファイル」とみなされ、`Permission Denied` でエラーになる。
    - **対策**: `.env` で `UID=${UID}` を渡し、`docker-compose` 内で `user: "${UID}:${GID}"` を指定することで、コンテナが「あなた（ホスト側と同じ ID）」として動くように設定する。
- **相対パスの可搬性 (Portability)**:
    - **問題**: `docker-compose.yml` に `../stock-ops` と書くと、二つのリポジトリが「常に隣同士」にいないと動きません。
    - **懸念**: あなたが将来的にフォルダ構成を変えたり、あるいは CI（自動テスト）環境に持っていった時に、「マウント対象が見つからない」というエラーで悩みやすくなります。
    - **対策**: 環境変数（例：`OPS_DIR`）を使い、デフォルト値は隣を指しつつ、必要に応じて場所を上書きできるように抽象化します。
- **設定（STRATEGY_DIR）の同期**:
    - **問題**: 「ホスト側のパス」と「コンテナ内のパス」の食い違いです。
    - **具体例**: あなたの PC 上では `/home/irom/dev/stock-ops` ですが、コンテナ内では `/app/external/strategy` にマウントされます。プログラムに教えるべきなのは後者（コンテナ内）のパスです。
    - **懸念**: 誤ってホスト側のパスをコンテナに渡してしまうと、コンテナ内で「そんなフォルダはない」と怒られてしまいます。
    - **対策**: `docker-compose.yml` の中でマウント先を固定し、それと連動するように `STRATEGY_DIR` をコンテナ側に自動注入する仕組みを作ります。
- **ホットリロードの有無**:
    - YAML を書き換えた際、コンテナを再起動せずに反映させる仕組みが必要か。現状は起動時ロードのため、テストサイクルを回すには高速な再起動が求められる。

### 2.6 ダッシュボード公開とセキュリティ (New)

GitHub Pages を利用したログ・レポートのダッシュボード化について。

- **リスク: 公開性のトレードオフ**:
    - GitHub Pages は **デフォルトで全世界に公開** される。
    - 分析ログやレポートには、具体的な「監視銘柄」「売買スコア」「戦略の適用結果」が含まれるため、これを公開することは自身の投資行動（アルファ）を全て公開することに等しい。
- **対策案**:
    - **案A (Local First)**: `stock-ops` 内に簡単な HTML レンダラーを用意し、ローカルブラウザでのみ閲覧する。
    - **案B (Strictly Public Only)**: `core` 側の統計情報（エラー率や実行時間など、銘柄を含まないメトリクス）のみを抽出して GitHub Pages に送る。
    - **案C (Private Pages)**: GitHub Enterprise または有料プランの Private Repository + Private Pages を利用する。

**論点6**: ダッシュボードに「何を」載せたいか？（テクニカルな生存確認か、投資判断の可視化か）

## 3. 設計の進化：目新しさと本質的価値 (v29.3)

これらの「工夫」は一般的な Docker のベストプラクティスではあるが、本プロジェクトの **「リポジトリ間ゼロトラスト (Zero-Trust between Repositories)」** という特殊な文脈において、以下の決定的な価値を持つ。

1. **「便利さ」から「堅牢さ」への転換**:
    - シンボリックリンクを捨てたことで、Core 側は Ops 側が「どこにあるか」「誰が持っているか」を一切考慮しなくて良い。この **「エンジンの不可知性（Agnosticism）」** が、将来のプロダクト化の根幹となる。
2. **「属人性」の排除と可搬性の実現**:
    - 一般論としての可搬性を、本プロジェクトでは「Public Core と Private Ops の安全な併走」のために再定義している。
3. **SSOT による契約的開発**:
    - Pydantic バリデーションが、Core と Ops の間の **「厳格な契約（インターフェース）」** として機能する。これにより、一方の開発が他方を意図せず壊すことを物理的に防止する。

**結論**:
技術自体は枯れた標準である。しかし、それらを組み合わせて「秘伝のタレ（戦略）」と「汎用鍋（エンジン）」の分離を、**安全性と開発効率を損なわずに完遂すること**にこそ、本フェーズの設計的価値がある。
