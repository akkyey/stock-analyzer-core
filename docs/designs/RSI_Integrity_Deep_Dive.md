# 設計深化：RSI欠損とデータ整合性の根本原因分析

## 1. 現状の課題
2026-03-17のスキャンにおいて、以下の2つの大きな問題が確認された。
- **RSIの欠損**: プロセスされた銘柄の多くでRSIが計算されず、レポートが「抜けだらけ」になった。
- **銘柄数の激減**: 本来約4,000銘柄あるはずのマスタが、DB（`stocks`テーブル）上で917件に減少しており、日次スキャンの対象が大幅に絞り込まれていた。

## 2. RSI欠損の論理的背景（Deep Dive）

### A. 計算ロジックと依存関係
RSI（Wilder's法）は `PolarsProcessor` で以下のように計算されている：
1. `Close` (終値) の履歴を取得。
2. `Close.diff()` で前日比を算出。
3. `ewm_mean(com=13)` で平滑化（Wilder's法）。

**財務データ（Fundamentals）との関係**:
論理的には無関係。ROEや自己資本比率がなくても価格さえあればRSIは計算可能。

### B. 欠損が起きた真の原因（仮説）
1. **yfinanceのロングテール/404エラー**: 
   並列取得時、一部の銘柄で価格履歴の取得に失敗。`PolarsProcessor` は `Close` が `null` の行を除去するため、履歴が14日分に満たない銘柄はRSIが算出されない。
2. **フィルタリングによる「見かけ上の欠損」**: 
   `daily` スキャンは最後にフィルタリング（売買代金XX以上等）を行う。財務データが壊れている銘柄がフィルタで落とされ、結果として「生き残った少数の銘柄」だけがレポートに載り、他が「抜けている」ように見えた。

## 3. 除外銘柄（ブラックリスト）管理戦略

無効な銘柄へのフェッチを繰り返す無駄を省き、スキャン速度とAPIクォータを最適化するため、以下の除外管理を導入します。

### 3.1. モデルの拡張 (`Stock` テーブル)
- **`is_active` (Boolean)**: デフォルト `True`。フェッチ対象にするかどうかのマスターフラグ。
- **`status` (String)**: `active`, `suspended`, `delisted`, `ipo_cooling` 等。
- **`exclusion_reason` (String)**: なぜ除外されたかの理由（例: "404 Not Found", "Insufficient history for technicals"）。
- **`excluded_until` (Date)**: 再開予定日（IPO銘柄の待機期間など）。

### 3.2. 除外のパターン
1. **恒久除外 (Hard Blacklist)**:
   - 上場廃止が確認された銘柄。
   - ユーザーが明示的に除外を希望した銘柄（ETF、REIT等の対象外セクター）。
2. **一時時除外 (Soft Blacklist / Cool-off)**:
   - **IPO銘柄**: 上場後30日（RSI計算に必要な期間）が経過するまで自動的にスキップ。
   - **連続エラー銘柄**: フェッチが N 回連続で失敗した場合、一定期間（例: 7日間）スキャン対象から外し、サーバー負荷を軽減。

### 3.3. 運用サイクル：デイリー除外・ウィークリー復活審査

「デイリーは高速、ウィークリーは慎重」という二段階の運用を明確化します。

1. **Daily スキャン (高速)**:
   - **対象**: `is_active=True` の銘柄のみ（「精鋭部隊」のスキャン）。
   - **除外トリガー**: 取得失敗時、または計算不能時にその銘柄を「休止（`is_active=False`）」に落とします。
2. **Weekly スキャン (復活審査)**:
   - **対象**: 全銘柄（休止中を含む〜4,000件）。
   - **アクション**: 重厚な財務データフェッチとマスタ修復を実施。
   - **復活ロジック**: Weekly での取得とテクニカル計算が正常に成功した場合、`is_active=True` に戻して翌週からのデイリスキャンに復帰させます。
   - **レポーティング**: ウィークリーレポートに「復活（Active化）」「継続休止」「新規除外」といったステータス変化列を追加し、銘柄の当落を可視化します。

---
> [!TIP]
> これにより、IPO銘柄も「Weekly のタイミングで、十分な履歴が溜まったと判断されたらDailyに昇格する」という自動的なライフサイクル管理が可能になります。

## 4. 銘柄数激減のアーキテクチャ的要因

### アーキテクチャの変遷と不整合
- **旧設計**: 毎回JPXのCSVを読み込み、4,000件をメモリ上で展開してスキャン。
- **新設計 (v26.0以降)**: DBの `stocks` テーブルを「正」とし、そこにある銘柄のみをスキャン対象とする。
- **不一致の発生**: DBメンテナンス（`repair_master`）が未実行、または過去の制限付きテストの結果がDBに残り、917件が「全件」であるとシステムが誤認した。

## 4. 再発防止策と設計の深化

### 確実な復旧手順（承認待ち）
1. **マスタの再同期**: `weekly_fundamentals` はJPXリストを正としてDBを上書きするため、これを完遂させる。
2. **データ取得の堅牢化**: 今回導入した `YahooFetcher` の `Lock` により、並列取得時の `RuntimeError` を物理的に排除する。
3. **欠損値の可視化**: スキャン終了時に「価格取得失敗数」「期間不足数」をログに統計として出力するよう `ScanHandler` を強化する。

## 5. 棄却された案
- **案: スキャン時に毎回CSVを読み込む方式に戻す**
  - **理由**: DBを「Single Source of Truth」にする現在の方針に反し、速度も低下するため。DBマスタを `repair_master` で維持する方が現代的。
- **案: RSIが計算できない場合に前回の値を引き継ぐ**
  - **理由**: 移動平均乖離率やRSIは最新価格に敏感であり、古い値を出すと誤った売買シグナルを誘発するリスクがあるため。
