# Architecture Decision Log (ADR)

## 2026-03-17: Polars Query Engine Roleout (v23.1)

### Context
既存の Pandas ベースのスコアリングエンジン（V2）は、銘柄数が増加するにつれて Python のループオーバーヘッドが無視できなくなり、特に Daily スキャン時のボトルネックとなっていました。また、テクニカル指標の柔軟な拡張に対する型安全性の欠如も課題でした。

### Decision
1. **Polars Expression API への移行**: ベクトル化演算を最大限活用するため、Polars をコア演算エンジンとして採用。
2. **動的エンジン切り替え**: `use_polars` フラグにより、既存エンジンとの共存を可能に。
3. **ボリンジャーバンド (BB) の統合**: 逆張り指標として BB を追加し、計算とスコアリングを Polars で実装。

### Status
- [x] 実装完了
- [x] 100銘柄および全件スキャンによる検証完了。Calculation Phase の大幅な高速化（51ms）を確認。
- [x] Pydantic スキーマへの統合による型安全性確保。

### Consequences
- スコアリング演算自体はミリ秒単位まで高速化された。
- 支配的なボトルネックが「行単位の Pydantic バリデーション」に移動したことが判明。今後のさらなる高速化にはバリデーションのベクトル化が推奨される。

## 2026-03-17: [v26.4] 一括ベクトル演算の導入と堅牢性の向上

### 決定内容
1. **Batch Vectorization**: 銘柄ごとのループ計算を廃止し、Polars の `group_by` を使用したチャンク一括演算 (`calc_batch_technicals_vectorized`) を導入。
2. **CLI/Context デフォルト値の統合**: ストリーミングのレスポンスを高めるため、`chunk_size` のデフォルトを全コンポーネントで 50 に統一。
3. **ShapeError & TypeMismatch 対策**: 
    - `pl.concat(..., how="diagonal")` を採用し、列不一致時でも継続可能に。
    - `Volume` 列を結合前に `Int64` へ強制キャストし、yfinance 由来の型の揺れによる異常終了を防止。

### 背景
- 従来の v26.3 実装では Python ループのオーバーヘッドが大きく、全件スキャン時に数分レベルの遅滞が発生していた。
- また、MACD 等の指標計算不可銘柄や、型不一致（Volume の Int/Float 混在）による `ShapeError` / `ComputeError` が課題であった。

### 影響
- **速度**: 演算コストを Polars に寄せることで、計算フェーズが事実上ゼロコスト化した。
- **安定性**: 欠損データや型の不一致を正規化プロセスで吸収し、中断のないスキャンを実現。

## 2026-03-17: [v26.11-v26.12] 非同期パイプラインの堅牢化と例外処理の改善

### 決定内容
1.  **NameError (context) の修正**: `fetch_price_history_batch` における引数 `context` の伝播漏れを解消。
2.  **スレッド間タイムアウトの導入**: Fetcher スレッドのハングを防止するため、`queue.get(timeout=60)` を導入し、エラー発生時もメインスレッドが停止しないよう構成。
3.  **統計計測の正常化**: スレッド終了を待機するロジックを修正し、全ての処理済み枚数が統計に反映されるよう改善。

### 背景
- `yahoo.py` における初歩的な `NameError` により、パイプラインが実走初期にクラッシュしていた。
- 異常終了時にメインスレッドが永久待機に入るリスクがあり、タイムアウトによる自己防御が必須となった。

### 未解決課題（次回の設計深化/実装対象）
- **レポートデータ消失**: 現在のインメモリパイプラインでは財務データ（Fundamentals）が結合されておらず、フィルタリングで除外されている。
- **解決策**: `ScanHandler` 内で `Fundamentals` を一括取得し、Polars を用いてインメモリで `left_join` を行う「Polars完結型データフロー」を導入する。これにより変換オーバーヘッドも最小化する。
## 2026-03-17: RSI Wilder's Method Upgrade (v27.1)

### 決定内容
1. **Wilder's Smoothing の導入**: RSI 計算ロジックを SMA ベースから、Wilder 提唱の漸化式と数学的に等価な `ewm_mean(com=13, adjust=False)` にアップグレード。
2. **精度と応答性の向上**: これにより、強いトレンド時でも RSI が適切に推移し、当初の pandas 実装と同等の挙動を Polars で再現。

### 背景
- 従来の Polars 実装では `rolling_mean` を使用した SMA 近似を用いていたが、指数平滑化を用いる Wilder 本来の手法（Wilder's Smoothing）と比較して、トレンド転換時の応答性に差異があった。
- ユーザーからの指摘に基づき、より正確な Wilder 法の実装が求められた。

### 影響・教訓
- **環境制約**: `safe-shell` 環境（RLIMIT_NPROC=100）下では、Polars のデフォルトのマルチスレッド挙動が `could not spawn threads` を引き起こすことが判明。
- **回避策**: 制限環境下での検証には `POLARS_MAX_THREADS=1` 等の明示的な制御が不可欠である（Memory ID: 38 に記録）。
## 2026-03-18: [v28.0] Post-Deployment Issues in Polars Engine & Persistence

### 決定内容
1. **DB永続化の同期化（一時的措置からの脱却）**: `ScanHandler._deferred_persistence` における `daemon=True` を解除し、CLI実行時に全データの書き込み完了を保証することを決定。
2. **スコア内訳の再実装**: `PolarsEngine` 内で `score_value`, `score_growth`, `score_quality` 等のカテゴリー別集計を導入し、`StockReporter` への供給を再開する。

### 背景
- **持続的なデータ欠落**: 全件スキャン（3,934件）完遂後も、DBには数十件しか反映されていない致命的なバグが判明。これはデーモンスレッドの強制終了が原因。
- **Fundamental スコア 0.0**: 抽出されたわずかなデータも、スコア内訳の欠落によりファンダメンタル指標が 0.0 と出力されており、スプレッドシートが「空」に見える要因となっていた。

### 影響・教訓
- **ライフサイクル管理**: 非同期保存を導入する場合、CLIのような「一度きりの実行プロセス」においては、プロセスの終了前に保存完了を待機する仕組みが必須。
- **機能パリティの重要性**: エンジン移行（Pandas -> Polars）時には、単一の最終スコアだけでなく、ダウンストリーム（レポーター等）が依存している中間スコアの互換性も精査する必要がある。

## 2026-03-19: [v28.2] Logical Parity & Zero-Error Synchronization

### 決定内容
1. **Strict Null Handling**: PER 等の「低いほど良い」指標において、`null` が `0.0` と見なされ加点されるのを防ぐため、閾値判定の前に `is_not_null()` チェックを強制。
2. **Config Path Normalization**: ボラティリティペナルティ設定の取得元を `scoring_v2.penalty_rules` に修正し、グローバル設定との不一致を解消。
3. **Double-Verfication Flow**: `tools/verify_engine.py` を活用し、`Max Diff < 0.1` ではなく `Max Diff = 0.0000` を合格基準としてロジックを磨き込み。

### 背景
- エンジン移行後、130A銘柄（null PER）や 137A銘柄（高ボラティリティ）で Pandas版と最大 17.0 点の乖離が発生していた。
- これを放置するとランキングの信頼性が損なわれるため、完全一致を目指したリファクタリングを実施。

### 影響
- **精度**: 全 500 銘柄（Balanced Strategy）において、Pandas版と Polars版の全スコアが完全一致（誤差 0.0）することを実証。
- **保守性**: デバッグコードを排除し、設定ファイルの構造に忠実な Expression 構築フローに整理。

## 2026-03-26: [v29.0] Plugin Architecture & Repository Decoupling

### 決定内容
1. **リポジトリの物理的分離**: 汎用エンジン (`stock-analyzer-core`) と、秘伝の戦略・運用環境 (`stock-ops`) を別ディレクトリ（将来の別リポジトリ）に隔離。
2. **プラグイン型戦略注入**: エンジン側のコードを改変せず、外部ディレクトリ（隣接フォルダまたは環境変数指定）から YAML を動的にマージする機構を導入。
3. **ハイブリッド・テスト戦略**: エンジン基盤テストは Public、秘伝の戦略に依存する回帰テストは Private に配置。

### 背景
- コアロジックの OSS 公開によるコミュニティ貢献と、独自の投資戦略（有料級）の秘匿・マネタイズを両立させる必要があった。
- 密結合な状態では、意図せず戦略パラメータが Public に流出するリスクが高いため、物理層での隔離を断行。

### 検討中のリスクと課題（DEEPEN モード継続中）
1. **外部リンク（シンボリックリンク）の完全撤去**: 
    - **決定**: 公開予定の `stock-analyzer-core` 内からは、`gemini-docs` へのシンボリックリンクをすべて取り除く。
    - **理由**: 「戻し忘れ」による Private 資料の誤公開リスクを物理的にゼロにするため。
    - **運用**: 開発の経緯や旧ドキュメントは、すべて `stock-ops` または元の `gemini-docs` 側でのみ閲覧し、Core リポジトリは純粋に「プログラムの器」として維持する。
2. **「よそ行き資料」の新規作成フェーズの分離**:
    - **決定**: 将来の OSS 公開時に必要となる外部向けドキュメントは、この整理フェーズでは作成せず、後日「広報・ドキュメント作成フェーズ」として別途安全に実施する。
2. **プラグインの安全性と検証**:
    - 外部 YAML のロードにおけるインジェクション耐性。
    - **対策案**: `yaml.safe_load` の徹底、およびスキーマバリデーションの強化。
3. **運用ミスによる Private 情報の混入**:
    - Docker ビルド時に Private なマウントポイントを誤って COPY してしまう等。
    - **対策案**: Docker context の厳格な制限と、ビルド済みイメージの自動セキュリティスキャン。

## 2026-03-30: [v30.0] 429 Rate Limit Avoidance & RSI Stabilization

### 決定内容
1. **完全シングルスレッド化 (Serial Fetching)**: `MarketFetcher` の `MAX_WORKERS` を 1 に固定し、yfinance への並列リクエストを廃止。
2. **待機戦略 (Jitter & Backoff) の強化**:
    - `FundamentalsFetcher` に 0.5s 〜 1.5s のランダム待機を導入。
    - 指数バックオフの最大待機時間を 60秒、リトライ回数を 5回に強化。
3. **RSI 信頼性ガードの実装**:
    - 算出に必要な最小サンプル数を 14日 から **30日** に引き上げ（Wilder 法の収束を保証）。
    - 履歴データ不足時に自動で `period="1y"` をフェッチする動的期間選択を導入。
    - スコアリングエンジンにて、RSI 0/100 を「非営業日ノイズ」として除外するフィルタリングを実装。

### 背景
- 2026-03-27 以降、Yahoo Finance のレート制限（429）が厳格化し、従来の並列フェッチではスキャンが完遂できない事態が発生していた。
- また、休日（3/20 等）のデータが 0 として記録されることで、RSI が 0 や 100 に張り付く異常値が発生し、ランキングの信頼性を著しく損なっていた。

### 影響
- **安定性**: 1.8M 件の `weekly_market` 全件再構築において、429 エラーなしでの完走を実証。
- **データ品質**: 異常値による「過熱感」の誤判定が消失し、分析結果の信頼性が回復した。
- **トレードオフ**: フェッチ速度は低下したが、中長期的な運用安定性を最優先する設計へと転換した。
