## 1. 実行環境ごとの違い

本ツールは、Colab だけでなく、ローカルの CLI（Linux・macOS・Windows）、Docker でも使われる想定です。環境によって、設定の渡し方・DB の置き場所・永続化が違います。

| 環境 | 取り直しの設定の渡し方 | DB の場所 | 永続化 | EDINET キー | 既知の注意 | 今回の検証 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Colab** | Step 0 の `refetch_edinet_year` → Step 3 が `fetcher.edinet_scan_days = 365` を設定 | `/content/working`（SSD） | 実行の最後に Drive へ同期 | Step 2 の設定（環境変数） | 途中で切断されると、Drive には反映されない（次回また取り直す） | ユーザーが実機で確認（未実施） |
| **ローカル CLI**（Linux・macOS・Windows） | **CLI に引数が無い**。`config/config.yaml` を書き換えるか、検証用スクリプトで設定する | 既定は リポジトリの `data/`（**本番の DB と同じ場所**）。`STOCK_ANALYZER_BASE_DIR` で変えられる | ローカルのディスク | `.env` の `EDINET_API_KEY` | 下記 §2 の指摘 A。Windows・macOS は未確認 | Linux（本機）で実施予定 |
| **Docker** | 不明 | 不明 | 不明 | 環境変数で渡す想定 | **起動できない**: `Dockerfile` の ENTRYPOINT が `src/orchestrator.py` を指すが、このファイルは存在しない（§2 の指摘 B） | 対象外（修正後に判断） |
| **GitHub Actions**（有料版の構想・未実装） | 未定 | ランナーごとに新しい（DB が残らない） | 無し（キャッシュ・アーティファクトが必要） | Secrets | 毎回が初回扱いになる。取り直しを毎回入れると EDINET への負荷が大きい（§2 の指摘 D） | 対象外（未実装） |

### 1.1 ローカル CLI で設定を渡す方法

- `python -m src` には、取り直しの引数がありません。
- 検証では、`scratchpad/run_check.py`（Colab の Step 3 と同じく、`context.config` を書き換えてから `ScanHandler` を実行するスクリプト）を使います。
- `config/config.yaml` の `fetcher.edinet_scan_days` を直接書き換えることもできますが、**残すと毎回の実行が 365 日分の走査になるため、検証後に必ず戻すこと**（§2 の指摘 A）。
- 必ず空の作業ディレクトリ（`--base-dir`）を指定してください。既定の `data/` は、本番の DB と同じ場所です。

### 6.5 設計上の指摘（環境別の検証で確認したこと）

- **指摘 A（再掲）**: `config.yaml` の `edinet_scan_days` を 365 のまま残すと、毎回の実行が 365 日分の走査になる。CLI には取り直しの引数が無いため、一度だけの指定の仕組みが要る。
- **取り直しの所要時間**: 計画の約 100 分に対し、実測は 126.9 分（市場データ取得を含む全体）。EDINET 同期だけの時間は、ログから分けられない。
- **取り直しの効果**: 空の DB でも、新しい開示が反映されて件数が増えた（+141 銘柄）。

### 6.6 V5 の結果（取り直しの途中中断と再開・ローカル CLI）

手順: 空の作業ディレクトリで取り直し（365 日）を開始 → 取得済みの書類が約 1,500 件の時点でプロセスを強制終了 → 同じ作業ディレクトリで再実行。

| 段階 | 結果 |
| :--- | :--- |
| 中断時の状態 | 取得済みの結果ファイル（`tmp/edinet_results`）1,513 件。**走査日の記録（`edinet_last_scan_date`）なし**。データベースの `edinet_documents` は空 |
| 再実行 1（取り直しなし・既定の 30 日） | 30 日分だけ走査（新たに 100 件、キャッシュ利用 190 件、反映 1,613 件）。**中断した 365 日分の残りは、取り込まれない**（走査日の記録がないため、既定の 30 日になる） |
| 再実行 2（取り直し 365 日を再指定） | 保存済みの結果を再利用（キャッシュ利用 1,616 件）。新たに取得 3,434 件。合計 5,032 件で、V2（中断なし）と同じ件数 |

**結論**
- 中断しても、**同じ作業ディレクトリが残っていれば**、取り直しを再指定すると、取得済みの分は再取得されず、続きから取り込まれる。
- 取り直しを再指定しないと、残りは取り込まれない。画面にも、取り直しが未完了であることは出ない。
- 一覧（過去 365 日分）の取得は、毎回やり直しになる（数分）。
- **Colab では、セッションが切れると作業ディレクトリ（`/content/working`）が消える**ため、保存済みの結果は失われ、最初からやり直しになる。データベースの `edinet_documents`（書類の処理済みの記録）は、書類を反映した後に記録されるため、中断時には残らない。Drive へ同期されるのも、実行が完了したときだけ。
- 以上は ローカル CLI（Linux）での実測。Colab での中断は未検証。
