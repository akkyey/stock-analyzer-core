## 4. v1.3.1: 財務シードの作り直し

### 4.1 背景

同梱の財務シード（`src/resources/fundamentals_seed.parquet`）は、生成手順がリポジトリに無く、次の問題があった。

- 約 4 割の銘柄で、EPS・BPS・純利益などが空（Colab の診断サマリで、`eps` が 3,927 銘柄中 2,453）。
- 旧シード由来の誤った値が含まれる（例: トヨタの自己資本比率 74.76%。有価証券報告書の値は 37.8%）。
- シードを DB に入れるのは、財務データが 3,000 件未満の初回構築だけで、EDINET の同期も過去 30 日分の書類を出した銘柄しか更新しない。そのため、**既存の利用者の DB には、旧シード由来の値が、次の決算の提出まで、最長で約 1 年残る**。

### 4.2 作り直しの方式

`scripts/build_fundamentals_seed.py`（新規）。パイプラインと同じ処理（EDINET の取得 → パーサー → 決算期の新旧判定つきの反映）を、作業用の空の DB に対して、全社分（過去 400 日）で実行し、シードの列構成で書き出す。新しい取り込みロジックは持たない。

- 旧シードの列に、出所の列（`period_end`・`submitted_at`・`bs_period_end`・`bs_submitted_at`）を加える。旧シードにあって DB に無い旧い状態列と、`updated_at`（株式分割の補正の基準日）は、旧シードの値を引き継ぐ。
- 旧シードの銘柄と、現在の JPX の上場銘柄だけに絞る（EDINET には、銘柄マスタに無い提出者 153 件も含まれ、そのまま入れると、画面の銘柄数が食い違うため）。
- **公開用は、空の作業ディレクトリで 1 回の実行で作る**。使い回すと、前回の取得結果が混ざり、同じ銘柄で、訂正報告書と原本のどちらの提出日時になるかが、実行ごとに変わる（14 銘柄で確認）。空でない場合は `--reuse` が無いと実行しない。

### 4.4 取り込みのガードと、既存 DB への反映

**取り込みのガード（`EdinetBridge`）**

| ガード | 内容 | 理由 |
| :--- | :--- | :--- |
| 自己資本比率の範囲 | -1000〜100% の範囲外は採用せず、純資産 / 総資産で補えれば補う | 総資産が 0 と読まれた書類（543A）で、-4.08×10¹⁰% になった。債務超過の -109.1%（4381）は、実際にあり得る値として採用 |
| 発行済株式数 | 1,000 株未満の書類では、株数と 1 株当たりの値（EPS・BPS・DPS）を採用しない | 上場前に提出された 543A は 1 株で、EPS・BPS が約 -4 億円になった |
| 売上高成長率 | 売上が **DB の値から変わったときだけ**、`sales_growth` を空にする | 旧い売上との比較の値が、新しい売上と食い違うため。同じ決算期の売上なら、整合しているので残す |

`sales_growth` は、スコア・判定・足切りには使われず、レポートの `Sales_Growth` 欄の表示だけに影響する（旧シードで成長率のある 1,612 銘柄のうち、売上が変わったのは 194 銘柄）。

**既存 DB への一度だけの反映（`FundamentalsRepository.refresh_from_seed`）**

- EDINET 取り込みと同じ規則で、銘柄ごとに、損益・1 株当たり指標は `period_end`、貸借対照表の項目は `bs_period_end` を比べ、シードの期が DB より新しいか、DB の期が不明（旧シード由来）の項目だけを更新する。シードの値が空の項目は、DB の値を消さない。
- 実行済みの印は `app_meta.fundamentals_seed_refreshed`。値はシードの内容から作る識別子で、シードを作り直すと、もう一度反映される。新規の DB は、読み込んだシードが最新なので、印だけを残す。旧版で消えた値の復旧（`fundamentals_restored_parser_v2`）より先に実行する。
- 切り替え: 設定 `fetcher.refresh_fundamentals_from_seed`（既定 true）。Colab では、Step 0 のチェックボックス `refresh_fundamentals`（既定 ON）。外して実行した場合は、印を残さないので、あとで有効にして実行できる。
- 画面に「財務データを、新しい版の同梱データで N 銘柄更新しました」と出す。

**別のノートブックにせず、同じノートブックのチェックボックスにした理由**: 別のノートブックは、存在を知らない利用者が、古い（誤りを含む）値のままになる。初期値 ON のチェックボックスなら、何もしなくても更新され、更新したくない利用者は、外すだけで止められる。

### 4.7 副次的に見つけた既存の不具合: `fetcher:` 設定の脱落

「反映を切る」設定で実行しても、反映が実行されたことで見つかった。

- **原因**: 設定のスキーマ（`ConfigModel`）に `fetcher` の項目が無く、`extra: ignore` のため、`defaults.yaml` と `config.yaml` の `fetcher:` の内容が、CLI では、読み込み時にすべて捨てられていた。
- **影響**: `edinet_scan_days` などは、コード内の既定値（YAML と同じ値）が使われていたため、気付かれなかったが、設定ファイルでの切り替えは、一切効かなかった。Colab は、ノートブックから設定を直接渡すため、影響を受けない。
- **対応**: `fetcher: dict[str, Any]` を追加し、辞書のまま通す（`21fe328`）。YAML の値は、コード内の既定値と同じか、コードで参照されていないため、既存の動作は変わらない。

## 8. 追補（2026-10-06 午後）

### 8.1 BPS と「純資産 ÷ 発行済株式数」のずれの原因と修正

§4.6 で「原因未調査」としていた、1 株当たり純資産（BPS）と株数のずれを、EDINET の原本で調べて特定し、修正した（`b4b5a80`、`7b5f864`）。

- **原因**: 有価証券報告書の EPS・BPS は、期末後・提出前の株式分割や併合を反映して算定し直される（書類の注記に「株式分割調整後の数値を記載」）。パーサーは、株数を、要約表の**期末時点**の値で読み、基準が食い違っていた（3443 は 2026-04-01 に 3 分割。期末 17,474,210 株、提出日現在 52,422,630 株）。株数が分割前のままなので、**時価総額が分割比率の分だけ小さく出ていた**（PER・PBR は影響しない）。
- **修正**: 提出日現在の発行済株式数（`FilingDateInstant`）を優先して読む。パーサー版を 3 に上げる。既存 DB への反映は、同じ決算期でも、シードの提出日時が DB 以降なら反映する（本番の DB にも、新しい株数が届く）。
- **ずれの分類**（BPS が正で、純資産・株数が正の 3,691 銘柄）: ①期末後の分割・併合（不具合。整数倍にぴったり一致する銘柄が 68 → 8）、②自己株式、③非支配株主持分、④半期報告書による更新（BPS が年次のまま）、⑤親会社の持分が負で純資産は正（15 件。実在し得る値）。②〜⑤は不具合ではない（詳細: 設計書 3.3）。
- **1 株当たりの値のガード**: 株数 1,000 株未満（上場前に提出された書類）、純資産 / (株数 × BPS) が 3 桁以上ずれる書類は、1 株当たりの値を採用しない（543A）。
