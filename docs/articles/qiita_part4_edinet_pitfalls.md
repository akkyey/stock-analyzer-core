## 第1章：何が起きていたか

最初に気づいたのは、レポートのPBR・配当利回り・営業利益率が、一部の銘柄で「-」（欠損）になっていることでした。調べると、直近30日に半期報告書を提出した69社で、DBの純利益・売上・営業利益・BPSが**すべてNULL**になっていました。

エラーも警告も出ていません。取り込みは「成功」していて、値だけが消えていました。

| 項目 | 半期報告書を取り込んだ69社の欠損数 |
| :--- | ---: |
| 純利益 | 69 |
| 売上 | 69 |
| 営業利益 | 69 |
| BPS | 69 |

この69社で終わるなら小さな問題ですが、**3月決算企業の半期報告書は11月に集中**します。2025年11月1〜30日の書類一覧をEDINET APIで集計すると、半期報告書（`docTypeCode=160`）が2,333件、有価証券報告書（120）が101件でした。30日窓で選ばれる書類は、約2,300社分のうち大半が半期報告書になります。つまり**11月には、全銘柄の約6割で財務値が消える**計算でした。

全銘柄で消えた場合の影響を、実DBから再計算して試算しました。

- 判定（Grade）が変わる銘柄：203件（B→C 150件、A→B 51件など）
- スコア上位100のうち、33銘柄が入れ替わる

しかも、この状態は**翌年の有価証券報告書が出るまで続きます**。

## 第2章：落とし穴① 半期報告書は `CurrentYear*` を持たない

### 症状の原因

旧パーサーは、XBRLの各値のコンテキスト（`contextRef`）に `CurrentYearDuration` などの文字列が**含まれる**かで探していました。

```python:src/fetcher/edinet_parser.py
CONTEXTS = {
    "current_i": "CurrentYearInstant",
    "current_d": "CurrentYearDuration",
    "prior_i": "Prior1YearInstant",
    "prior_d": "Prior1YearDuration",
}
# ...
if target_ctx in ctx_ref:   # 部分一致
```

有価証券報告書ならこれで動きます。しかし、**半期報告書のコンテキスト名は別物**です。

| 書類 | 当期（期間） | 当期末（時点） | 前期 |
| :--- | :--- | :--- | :--- |
| 有価証券報告書 | `CurrentYearDuration` | `CurrentYearInstant` | `Prior1Year*` |
| 半期報告書 | `InterimDuration` | `InterimInstant` | `Prior1Interim*`（前年同期）、`Prior1Year*`（前期通期） |

半期報告書には `CurrentYear*` が存在しないので、旧パーサーは**「前期通期」の値を拾っていました**（`Prior1YearInstant` の総資産・純資産、`Prior1YearDuration` のEPS）。売上や純利益のように、前期通期の値が別のタグにしかないものは取れず、`None`のまま残ります。

### 本当の被害は、ここから

パーサーが `None` を返しただけなら被害は出ません。被害を出したのは、**取り込み側が `None` をそのままUPSERTしていた**ことです。

```python:src/collector/financial_sync.py
record = {
    "net_profit": data.get("net_profit"),   # 取れなければ None
    "sales": data.get("sales"),
    ...
}
self.repository.upsert(records)   # None のまま上書き
```

既にDBにある正しい値を、`None` で消していました。さらに、総資産・純資産・EPSには**前期通期の古い値が、新しい値として書き込まれていました**。

### 直し方

- 書類の種類（有報／半期）をコンテキストから判定し、半期報告書は**期末時点の貸借対照表の項目だけ**（総資産・純資産・自己資本比率・発行済株式数）を採用する（半期分の利益や1株当たり指標は、年間値と混ざるため不採用）
- 取り込みは**取れた項目だけ更新**する（NULLでは上書きしない）

## 第3章：落とし穴② 連結と単体、そしてIFRS

### 部分一致が拾うもの

コンテキスト名には、`CurrentYearDuration` の後ろにメンバー名が付くことがあります。

- `CurrentYearDuration` … 連結
- `CurrentYearDuration_NonConsolidatedMember` … 単体
- `CurrentYearDuration_RetainedEarningsMember` … 株主資本等変動計算書の内訳
- `CurrentYearDuration_jpcrp030000-asr_..SegmentReportableSegmentMember` … セグメント

`"CurrentYearDuration" in ctx_ref` の部分一致だと、**単体・内訳・セグメントの値も通ってしまいます**。XBRL内の出現順で最初に見つかったものを採用するので、単体が先に出てくる書類では単体の値が採用されます。

### IFRS企業は、タグ名も違う

加えて、IFRS採用企業は要素名が違います（日本基準の `NetSales` に対して `RevenueIFRS`、`OperatingIncome` に対して `OperatingProfitLossIFRS` など）。旧パーサーはIFRSのタグを持っていなかったため、IFRS企業では連結の値が見つからず、**単体（日本基準で作る個別財務諸表）の `NetSales` を拾っていました**。

実例がニデック（6594）です。

| 項目 | 旧パーサーが拾った値 | 連結の正しい値 |
| :--- | ---: | ---: |
| 売上 | 2,735億円（単体） | 2兆7,087億円 |
| 純資産 | 190億円（単体） | 7,942億円 |
| ROE | 16.27%（同梱シードの値） | −55.5% |

IFRS企業は大型株が多いので、件数以上に影響が重い不具合でした。

### 直し方：「主要な経営指標等の推移」から読む

有価証券報告書の冒頭に、「主要な経営指標等の推移」という表があります。この表は**会計基準を問わず全社が開示**し、XBRLでは `*SummaryOfBusinessResults` という要素名になっています。

- 連結の値は、メンバーの付かないコンテキスト（`CurrentYearDuration` など）
- 単体の値は、`_NonConsolidatedMember` 付きのコンテキスト

この表には売上・純利益・総資産・純資産・自己資本比率・ROE・EPS・BPSが揃っています（営業利益だけは表に無いので、財務諸表本体から読みます）。これを**コンテキスト完全一致**で読みます。会計基準ごとの要素名は、優先順に並べた表で持ちます。

```python:src/fetcher/edinet_parser.py
SUMMARY_FIELDS = [
    # (項目, 期間種別, 候補の要素名 (優先順), 単体を常に許容するか)
    ("sales", "duration", (
        "NetSalesSummaryOfBusinessResults",              # 日本基準
        "RevenueIFRSSummaryOfBusinessResults",           # IFRS
        "OperatingRevenueSummaryOfBusinessResults",      # 営業収益
        ...), False),
    ("dps", "duration", ("DividendPaidPerShareSummaryOfBusinessResults",), True),
    ...
]
```

連結の値が**1つも無い**会社（子会社の無い会社）は、単体の値を使います。配当と発行済株式数は、提出会社（単体）の値として報告されるため、常に単体を許容します。333件で数えると、連結が257件、単体のみが65件（約2割）でした。単体のみの会社が約2割あるので、「連結が無ければ単体」の分岐は必須です。

### ハマりどころ：名前に反して中身が違うタグ

IFRSには、名前と中身が食い違う要素があります。

- `EquityToAssetRatioIFRSSummaryOfBusinessResults` … 名前は「自己資本比率」だが、中身は**BPS**（ニデックで `692.80`）
- 自己資本比率は `RatioOfOwnersEquityToGrossAssetsIFRSSummaryOfBusinessResults`（`0.256`）

名前だけでタグを選ぶと、BPSを自己資本比率として取り込みます。**値の桁と単位で、実データと突き合わせて確認する**のが安全です。

また、比率（ROE・自己資本比率）はXBRLでは小数（`0.138` = 13.8%）で入っているので、%に換算して保存します。

## 第4章：落とし穴③ ROEと自己資本比率が、ずっと更新されていなかった

取り込みの `record` には、ROEの項目自体がありませんでした。自己資本比率は、`equity_ratio` が**NULLのときだけ**、総資産と純資産から再計算していました。同梱シードに値がある銘柄は、一度も更新されません。

出力レポートのROEの出所を数えると、2,090件中2,086件が「stored」（シード由来）でした。

新しい有価証券報告書がある180社で、EDINETの値と同梱シードの値を比べました。

| 項目 | 3ポイント以上ずれた社数 | 10ポイント以上ずれた社数 |
| :--- | ---: | ---: |
| ROE | 79 | 24 |
| 自己資本比率 | 69 | 18 |

ROEは配点が最大の項目（30点満点）で、ずれの影響で**36社のスコアが5点以上変わっていました**。

### 直し方と、順番の罠

書類の報告値（`RateOfReturnOnEquity...`、`EquityToAssetRatio...`）をそのまま使い、報告が無い場合だけ、純利益÷純資産などで補います。

**順番に注意が必要でした。** ②（IFRS・単体の誤読）を直す前にROEをEDINETから計算すると、ニデックは純資産190億円（単体）で割って**ROE −880%**になります。さらに、自己資本比率が1%未満のときに自動で100倍する補正が入っていたため、誤読した0.98%が98%として扱われていました。**読み取りを直してから、更新を足す**必要があります。

## 第5章：落とし穴④ 過年度の訂正報告書

第1弾では、訂正有価証券報告書（130）を拾えるように、「**提出日時が新しいものを優先**」としていました。しかし、これでは足りませんでした。

企業は、ある日に**複数年度分の訂正報告書をまとめて提出**することがあります。たとえばある会社は、2026年9月3日の12時34分から12時40分にかけて、2021年6月期から2025年6月期まで5年分の訂正有価証券報告書を提出していました。別の会社は、最新期の訂正の後に、前期分の訂正を提出していました。

このとき、「提出日時が最も新しい書類」が**古い期の訂正**になります。すると、新しい期の値を、古い期の値で上書きしてしまいます。

2025年11月の書類一覧で、選択ロジックを再現したところ、**6社で2〜4年前の期の訂正報告書が選ばれていました**（例：2023年3月期）。9月の書類では0件でした。月によって再現するかどうかが変わるので、気づきにくい不具合です。

### ハマりどころ：一覧APIの `periodEnd` が訂正報告書では空

対象期間で選ぶには、書類一覧の `periodEnd` を使いたいところですが、**訂正報告書は `periodEnd` が空**でした（9月の訂正68件がすべて空）。書類名（`docDescription`）から取るしかありません。

```
訂正有価証券報告書－第27期(2024/04/01－2025/03/31)
```

```python:src/fetcher/edinet_parser.py
_PERIOD_RE = re.compile(r"(\d{4})/(\d{2})/(\d{2})")

def doc_period_end(doc):
    pe = (doc.get("periodEnd") or "").strip()
    if pe:
        return pe[:10]
    dates = _PERIOD_RE.findall(doc.get("docDescription") or "")
    if dates:
        y, m, d = dates[-1]      # 最後の日付が期末
        return f"{y}-{m}-{d}"
    return ""
```

### 直し方

- 書類は「**対象期間が最も新しいもの**、同じ期なら提出日時が新しいもの」で選ぶ
- 期末が約16か月（480日）より古い有価証券報告書は選ばない
- DBに、財務値の**出所（決算期末・提出日時）**を記録し、それより古い期の書類では上書きしない

## 第6章：地味だが効いた、取り込みの設計

### ① 抽出ロジックに「版」を持たせる

パーサーを直しても、旧版で処理済みの書類は「処理済み」としてキャッシュされ、取り込み直されません。**パーサーの版（`PARSER_VERSION`）を、結果と処理済みテーブルの両方に記録**し、旧版で処理した書類は自動で取り込み直すようにしました。

### ② キャッシュは「ファイルがあるか」でなく「同じ書類を同じ版で処理したか」

第1弾でも触れた `os.path.exists` によるキャッシュ判定は、第2段のローカルキャッシュにも残っていました。書類ID（`docID`）と版の一致で判定するように変えました。

### ③ 走査期間は「前回の走査日から」

「過去30日をスキャンする」だけでは、**30日以上実行しないと、その間に出た書類を取り逃します**。走査期間を、設定の30日と「前回の走査日から今日まで」の長い方（上限365日）にしました。一覧を取得できなかった日（通信失敗）があれば、次回その日から走査し直します。

### ④ 取り込む書類の種類を絞る

四半期報告書（140・150）は2024年4月に廃止され、現在出るのは過去分の訂正だけです。対象を120・130・160・170に絞りました。あわせて、証券コードが `00000` の書類（上場していない提出会社）は、4桁に切ると `0000` になって取り込まれていたので除外しました。

## 第7章：どう検証したか

### 実データのコーパスで、全件を通す

単体テストだけだと、実際の書類の多様さ（連結／単体、日本基準／IFRS／米国基準）に届きません。2026年9月に提出された書類333件のXBRLを、EDINET APIから取得して、新しいパーサーを全件に通しました。

- 連結257件、単体のみ65件、対象期間なし11件（有価証券報告書の様式でない書類など）
- 年度／半期の判定、連結／単体の判定は、全件で想定どおり

### 値どうしの整合性で、読み間違いを見つける

「ROE ≒ 純利益 ÷ 純資産」「EPS ≒ 純利益 ÷ 発行済株式数」のような**関係式で突き合わせ**ました。ずれた書類を1件ずつ見て、バグか、仕様どおりかを切り分けます。

- ROEが合わない書類は、期中に増資があったり、純資産が期首・期末の平均で計算されていたりして、バグではないものが多い
- 一方、IFRS企業の誤読のようなバグは、桁違いのずれとして出る

関係式で見つかったずれを「全部バグ」と扱うと、直しすぎます。**ずれの種類を分けて見る**のが大事でした。

### 同じ日のデータで、差分実行を繰り返す

旧版のDBから移行する場合と、空のDBから始める場合の2通りで、パイプラインを2回ずつ実行し、スコア・判定を比べました。同じ日のデータなら、**差分実行を繰り返しても結果が変わらない**はずです。旧版DBからの移行は全項目が一致し、空のDBからは1銘柄だけ食い違いました。この食い違いは、別の問題（株価のデータ不良）を示していました（下の補足）。

## まとめ：EDINETのハマりどころ

| # | ハマりどころ | 対策 |
| :--- | :--- | :--- |
| 1 | 半期報告書のコンテキストは `Interim*`（`CurrentYear*` ではない） | 書類の種類を判定し、半期は貸借対照表の項目だけ採用 |
| 2 | 取れなかった項目を `None` で上書きする | 取れた項目だけ更新する |
| 3 | 部分一致で単体・内訳・セグメントの値を拾う | コンテキストを完全一致で読む |
