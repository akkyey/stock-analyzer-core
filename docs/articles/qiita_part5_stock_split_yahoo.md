# yfinanceの日本株は株式分割を調整してくれない？ ― 偽の暴落、イベント欠落、異常な分割比率、そして自分の修正が引き起こした二重調整

> **【草稿】** 公開前。末尾の「草稿メモ」にフィードバック用の確認事項がある。公開時はこの引用と「草稿メモ」を削除する。

## TL;DR
- 日本株の株価履歴を `yfinance`（`auto_adjust=True`）で取っていたところ、**株式分割の段差が履歴に残る銘柄**があり、3:1分割の直後に「25日線乖離率 −64%、RSI 10」という偽の暴落シグナルが2か月続いていた。
- ただし、銘柄によって挙動が違う。初回取得で分割を261件検出したうち**258件はYahooが調整済み**で、**段差が残っていたのは一部**。さらに、**分割イベント自体を返さない銘柄**、**異常な分割比率（`2e-07`）を返す銘柄**、**イベント日が実際の段差の8日後**の銘柄もあった。
- 「イベントを信じて割る」だけでは壊れる。**株価の段差を自分で確かめ、段差が残っているときだけ調整する**設計にした。さらに、**私の修正自体にもバグがあり**（実行のたびに履歴が割られ続ける、100円未満の銘柄の値動きを併合と誤認）、実データで見つけて直した。その過程も書く。

---

## 概要

東証の約3,900社を毎朝取り込むパイプラインの監査で見つかった、株式分割まわりの不具合と、その直し方の記録です。財務データ側（EDINET）の話は別記事『[EDINETのXBRLで財務値が静かに壊れていた話](#)』に書きました。

> 動作環境：Ubuntu 24.04 LTS / Python 3.12 / Polars 1.x / yfinance。記載の挙動は**2026年10月時点の観測**で、非公式APIなので変わる可能性があります

---

## 第1章：偽の暴落

以前のDB（約125営業日分）に、しまむら（8227）の3:1分割が入っていました。テクニカル指標を計算し直すと、こうなります。

| 日付 | 終値 | 25日線 | 25日線乖離率 | RSI | トレンド点 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 2026-02-10 | 10,871 | 10,441 | +4.1% | 61.9 | 4 |
| 2026-02-20（分割後） | 3,537 | 9,741 | **−63.7%** | **9.7** | 0 |
| 2026-03-04 | 3,433 | 7,769 | −55.8% | 11.1 | 0 |

実際には株価はほとんど動いていません。分割前の値（約1万円）と分割後の値（約3,500円）が、同じ履歴に並んでいるだけです。移動平均が分割前の値を含むあいだ（75日線は約3か月）、**偽の暴落シグナルが続きます**。同じ形で、7946（5:1分割）は乖離率が−70%になっていました。

---

## 第2章：Yahooの挙動は、銘柄によって違う

「日本株の分割を調整しない」と一言でまとめたいところですが、実際に確かめると、少なくとも**5通り**ありました。

| パターン | 実例 | 起きること |
| :--- | :--- | :--- |
| ① 調整済み | 初回取得で検出した分割261件のうち258件 | 段差は無く、何もしなくてよい |
| ② 調整されない（段差が残る） | 8227（10,975円→3,713円）、7946 | 偽の暴落が出る |
| ③ イベント日が段差より後 | 329A・7176は8日後、8227・7946は1〜3日後 | イベント日の前後だけを見ると段差を見逃す |
| ④ イベント自体が無い | 8377（8,604円→836円、1:10）など | イベントを信じる設計では、まったく検知できない |
| ⑤ 異常な比率のイベント | 1909、2180、7082、7426が比率 `2e-07` 前後 | 信じて割ると、EPSが数百万倍になる |

⑤は、**①のように「調整済みだから何もしない」と決め打ちしても、②のように「イベントで割る」と決め打ちしても、どちらも壊れる**ことを意味します。

さらに、分割とは別に、**同じ異常値が連続する**データ不良もありました。上場直後の11日間が株価536億円（通常は約1,630円）という銘柄（8303）です。前日比で外れ値を除く方式だと、2日目以降は「前日比1倍」になってすり抜けます。

---

## 第3章：設計 ― 「段差が残っているときだけ調整する」

方針は次の3つです。

1. **イベントは「証拠」であって、命令ではない**。イベントがあっても、株価に段差が無ければ調整しない（①の対応）。
2. **イベントが無くても、段差が分割として妥当なら調整する**（④の対応）。
3. **異常な比率は、そもそも捨てる**（⑤の対応）。

### 段差を探す

イベント日の前後で、「前日比が分割比率に最も近い日」を段差の日とします。イベント日と実際の段差がずれる（③）ので、探す範囲はイベント日の14日前〜5日後にしました。

```python
SPLIT_SEARCH_BEFORE = timedelta(days=14)
SPLIT_SEARCH_AFTER = timedelta(days=5)

err = abs(math.log(prev / cur) - math.log(ratio))   # 前日比と分割比率の近さ
```

見つけた段差の日より前の行を、比率で割ります（出来高には比率を掛けます）。**段差が無い（調整済みの）履歴には何もしない**ので、何度適用しても結果は同じになる（はず。第4章で、そうならなかった話をします）。

### イベントが無い分割を推定する

④は、前日比が1.9倍以上（または1/1.9以下）で、整数比（2・3・5・10倍など）から5%以内の段差を、分割（併合）とみなして調整・記録します。10:1の分割で、前日比は10.3倍（8,604円→836円。連休を挟んで1営業日後）でした。

### 異常な比率を捨てる

⑤は、比率が0.02〜100の範囲外のイベントを捨てます。

### 1株当たり指標も補正する

株価だけ直しても足りません。**分割前に提出された書類のEPS・BPS・DPSは、分割前の株数が基準**です。これを分割後の株価で割ると、PERやPBRが分割比率の分だけ**割安に見えます**。

| 銘柄 | 分割 | 旧版の判定 | 旧版のPER | 修正後の判定 | 修正後のPER |
| :--- | :--- | :--- | ---: | :--- | ---: |
| 1926 | 4:1 | Grade S | 3.88 | Grade B | 15.52 |
| 5334 | 2:1 | Grade S | 8.11 | Grade B | 16.21 |
| 5805 | 5:1 | Grade A | 4.35 | Grade C | 21.76 |
| 6622 | 5:1 | Grade A | 4.65 | Grade C | 23.25 |

分割日が、値の基準日（書類の提出日時）より後なら、EPS・BPS・DPSを比率で割り、発行済株式数に比率を掛けます。基準日が分からない値は、二重の補正を避けるため補正しません。

## 第4章：自分の修正にもバグがあった

ここからが、一番書いておきたい部分です。

### 発見：実行のたびに履歴が割られ続けていた

修正後のパイプラインを、同じ日のデータで**2回続けて実行**して、DBを比べました（レポートのスコアは、比率で計算する指標が中心なので、**株価全体が定数倍されても変わりません**。レポートの比較だけでは気づけませんでした）。

| 4923の2026-03-23の終値 | 1回目 | 2回目 |
| :--- | ---: | ---: |
| 保存された値 | 1,273.76円 | **1,213.10円** |

1,273.76 ÷ 1.05 = 1,213.10。**差分実行のたびに、分割前の株価が1.05で割られ続けて**いました。4923には、比率1:1.05の分割イベントがあります。

### 原因：許容幅が、比率より広かった

段差を探す許容幅（対数で0.25）が、比率1.05（対数で約0.05）より広かったのです。比率1.05の分割は、日々の値動きと区別できません。**どの日も「段差」になり**、調整済みの履歴にも、もう一度適用されていました。

### 直し方

- 比率が1.9倍未満の分割は、**株価を調整しない**（財務側の補正にだけ使う）。
- 許容幅を、対数0.12に狭める。

### さらに：「値幅制限ではありえない」は誤りだった

イベントの無い分割を推定するとき、私は「値幅制限があるので、1営業日に1.9倍以上動くことはない」と書いていました。**これは誤り**でした。

東証の値幅制限は、基準値段ごとに決まっています。100円未満は30円です。**27円の銘柄は、1日で57円まで動けます**。実際に、6740は27円→52円（前日比1.93倍）と動き、「1:2の併合」と誤認されました。

そこで、**変化額が、その基準値段の制限値幅を超えるときだけ**、段差とみなすことにしました。

```python
_PRICE_LIMITS = (
    (100, 30), (200, 50), (500, 80), (700, 100), (1_000, 150), (1_500, 300),
    (2_000, 400), (3_000, 500), (5_000, 700), (7_000, 1_000), (10_000, 1_500),
    ...
)

def exceeds_daily_limit(prev, cur):
    return abs(cur - prev) > daily_price_limit(prev)
```

### もう1つ：「制限値幅の拡大」

値幅制限の表で判定しても、まだ誤認が残りました。**6072**です。2026年2月9日の引け後に、投資家グループのKaihouとの資本業務提携が発表され、翌日から**4日連続のストップ高**になり、1週間で株価は約8倍になりました。その途中で、328円→648円（約2倍、変化額320円）という日があり、これは「1:2の併合」に見えます。328円の制限値幅は80円なので、値幅制限の表だけでは「ありえない値動き」と判定されてしまいました。

実際には、**東証は、2営業日連続でストップ高（安）となり売買が成立しなかった銘柄の制限値幅を、翌営業日から拡大します**（通常の2倍など）。**4316**も同じで、4月1日・2日は出来高が約2万株・1.2万株とほぼ売買が成立しないままストップ安が続き、4月3日に387円→192円（出来高485万株）と、拡大した値幅で一気に下がっていました。どちらも併合ではありません。

そこで、**前日に制限値幅の80%以上動いた銘柄は、推定の対象から外す**ことにしました。

```python
def limit_may_be_widened(closes, i):
    pp, p = closes[i - 2], closes[i - 1]
    return abs(p - pp) >= 0.8 * daily_price_limit(pp)   # 前日に制限値幅まで動いた
```

6072・4316は、この条件で正しく外れます。一方、8377（10:1）のように、前日が静かな本物の分割は推定できます。

調整後に残った実際の大きな値動きを、再び段差と誤認して重ねて調整する不具合も、許容幅を狭めることで防げました。

---

## 第5章：どう検証したか

**同じ日のデータで、差分実行を繰り返して、DBを比べる**のが、一番効きました。冪等性（何度適用しても同じ）の問題は、1回目の実行結果だけを見ていても出ません。

- 旧版のDBから移行する場合と、空のDBから始める場合の2通りで、各2回実行した。
- 分割を記録した267件の履歴に、もう一度調整を適用して、**値が変わらないこと**を確認した（これで6740・6072の誤認を見つけた）。
- 既知の16銘柄（調整済み、段差が残る、イベント無し、異常比率、低位株）を、Yahooの最新データで再現し、**再適用しても結果が変わらない**ことを確認した。

## まとめ

| # | ハマりどころ | 対策 |
| :--- | :--- | :--- |
| 1 | 分割を遡って調整しない銘柄がある（調整済みの銘柄もある） | イベントを信じず、株価の段差を確かめて、残っているときだけ調整 |
| 2 | イベント日が実際の段差より、1〜8日後 | 探す範囲をイベント日の14日前〜5日後に広げる |
| 3 | 分割イベントを返さない銘柄がある | 値幅制限を超える整数比の段差を、分割とみなして推定 |
| 4 | 異常な分割比率（`2e-07`）を返す | 比率0.02〜100の範囲外は捨てる |
| 5 | 同じ異常値が連続して、前日比では除けない | 前後の中央値と、全期間の中央値からの乖離でも除く |
| 6 | 分割前のEPS・BPSを分割後の株価で割る | 分割日が基準日より後なら、比率で補正 |
| 7 | 比率が1に近い分割で、実行のたびに履歴が割られる | 1.9倍未満は株価を調整しない、許容幅を狭める |
| 8 | 「値幅制限ではありえない」を、比率だけで判定 | 基準値段ごとの制限値幅で判定（100円未満は30円） |
| 9 | 制限値幅の拡大で、急騰・急落が1日で2倍・半分になる | 前日に制限値幅の80%以上動いた銘柄は、分割の推定から外す |

一番の教訓は、**「修正が正しいか」は、1回の実行結果では分からない**ことです。同じ入力で、繰り返し動かして、**保存されたデータそのもの**を比べて、初めて見えた不具合でした。
